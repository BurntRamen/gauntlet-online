# Gauntlet Admin architecture

**Current implementation:** [Gauntlet Admin v1 — controlled authoring](gauntlet-admin-authoring.md) supersedes the read-only editing/publishing limitations below. This original inspection audit is retained as source and boundary context. Content and Game now share stored drafts, validation, presentation preview, immutable publication and rollback; Players and Matches remain inspection surfaces.

Inspected 2026-10-02 against the current local checkout, including pre-existing uncommitted gameplay, deck-workshop and asset changes. This describes the code in this checkout, not a claim that it has been deployed. No engine rewrite, database migration or content publication is included.

## Scope and access

The shell provides **Overview, Content, Game, Players, Matches, Publishing and System**. The new surfaces are read-only. System also retains the existing Studio active-room, season, collector and archive-recovery tools in an explicitly labeled expandable area. Existing archive import still requires its own preview and explicit commit; it is not part of content publishing.

Open `/admin/gauntlet` on the client, or use `/?admin=1` (`/?studio=1` remains an alias). Sign in using the existing Identity account login. Client deep links use the ordinary static React shell; it contains no private admin data. Every private request is independently authenticated by the Express server. Vercel rewrites cover the client deep-link path; they do not implement authorization. Direct requests to `/admin/gauntlet` and its descendants on the API server are also protected.

`server/adminAuthorization.js` allows exactly two **authenticated account IDs**, for simply and Burnt Ramen. `requireAccountRecord()` verifies the existing signed account session and reloads the account from the active account store before its ID is checked. Account display names, client flags, signed-token name claims, owner tokens and former owner sessions cannot grant access. Unauthenticated/expired/deleted accounts receive 401; authenticated accounts outside the allowlist receive 403; authorization storage errors fail closed. The namespace middleware runs before every `/api/admin/*` handler, including existing administrative mutations and unknown future endpoints. No general roles, invitations or permission editor exist.

- Production simply ID: `47d97ddb-65f9-4014-be92-9b677467d943`, confirmed against the existing production public account listing during this task.
- `GAUNTLET_ADMIN_SIMPLY_ACCOUNT_ID` can pin the corresponding existing account in another environment. The inspected local simply account has a different ID; it is not automatically added to the production allowlist.
- `GAUNTLET_ADMIN_BURNT_RAMEN_ACCOUNT_ID` must pin Burnt Ramen's stable ID. That ID was unavailable in the inspected records and has been requested from the operator. Until supplied, this slot is denied access. There is **no display-name fallback**. System reports an incomplete allowlist.
- Environment values define two named slots, not a general list. A missing, malformed or duplicate ID does not add another principal. The example environment file documents the settings. The former `OWNER_STATS_TOKEN` exchange no longer authorizes any admin endpoint; `/api/admin/session` now only reports the authenticated allowlist status.

The client checks `/api/admin/access` before rendering the shell. It clears protected state on logout, account switching, close, or an API 401/403, and ignores late authorization responses for a previous account. It reuses the application's existing account token; it creates no separate admin credential storage. Responses use `Cache-Control: private, no-store` (existing administrative handlers may use the equivalent `no-store`). CORS remains the existing application policy.

## Present engine seam

```text
Existing account / room authorization
  -> server/index.js: room creation, Socket.IO command validation
  -> shared/duel-rules: applyCommand, legal actions, perspective projection
     + server-owned campaign / AI / free-for-all behavior
  -> public perspective snapshots -> React / Babylon renderer
  -> matchRecords -> matchCompletion -> canonical record / evidence / archive
```

`shared/basic-gauntlet-rules/index.js` is a compatibility re-export of shared duel rules. The separate `server/game/gameFactory.js` / `gameLogic.js` files are legacy code, not the active `server/index.js` runtime entry point. Editing them would not safely configure the live engine. There is no single typed engine/content boundary yet.

The registry currently labels itself `gauntlet-content-v1` / `gauntlet-rules-v1`, while the shared duel engine uses `gauntlet-duel-v2` and `gauntlet-cards-v1`. Admin displays those distinct labels without claiming they are interchangeable or that the deployed client is at the same commit. The application package version is likewise not a release identifier. Deployment commit is shown only when supplied by the environment.

## Persistence and provenance

| Path | Current behavior | Admin treatment |
| --- | --- | --- |
| Preferred Supabase match storage | `gauntlet_match_records`, `gauntlet_match_events`, `gauntlet_match_consequence_receipts`, finalization/consequence RPCs. | Reads completed record JSON through existing storage conventions; does not modify schema or receipts. |
| Compatibility storage | Namespaced `match:<uuid>` journals in `gauntlet_faction_stats` when dedicated capabilities are unavailable. | Reads/validates journal envelopes and labels this source. Does not reconstruct results from account indexes. |
| Account-only fallback | Account consequences/indexes can persist while complete match records have weaker process/deployment retention. | Warns about evidence durability; does not count unavailable history as zero matches. |
| Local development | Account/match/faction JSON plus separate room snapshots and local canonical archive objects/indexes. | Strict read adapters report malformed files; no absolute private paths are returned by new system projections. Local disk durability depends on deployment volume lifecycle. |
| Canonical archive | Immutable record JSON plus `gauntlet_match_archive_index` and a private Supabase Storage bucket, or local equivalents. Existing validator verifies SHA-256 and structure. | Verified archived copies take precedence over storage copies. Corrupt or missing canonical objects generate a visible issue; the adapter does not conceal the failure with another copy. Exact lookup fails on corrupt canonical evidence. |
| Browser Match Library | `client/src/matchHistory.js`, IndexedDB, portable imports and local/offline completions. | Not remotely enumerable. Match browser scope explicitly excludes browser-only records. |

The match browser merges up to 100 recent entries from each server store, including guest-only matches, and searches this displayed window. It is not an all-time total or a complete historical index. Exact UUID lookup handles older records. Archive-only records are verified before being shown. Pending completion records are excluded. Players are paginated in stable ID order, 25 per page by default, with filtering clearly limited to the loaded page. Production account totals are not invented from a page of rows.

System reports a fresh account read and match read, cached persistence/archive capability status, registry validation, explicit schema versions and known source boundaries. It does not return environment variables, service keys, auth secrets, credentials, raw storage errors or private room data. Per-object archive verification occurs in match inspection. A running process necessarily passed registry startup validation; fatal startup validation failures cannot be diagnosed through an HTTP interface that never started.

## Adapter and API contracts

`server/adminData.js` contains the read-only projections; `server/index.js` injects existing pure encounter calculators, progression/collection/deck normalizers and persistence objects. Legacy deck normalization runs against a cloned account stats object so an admin read cannot save or mutate migrated data. No engine command is executed to calculate a preview.

| Route | Result |
| --- | --- |
| `GET /api/admin/access` | Existing account authenticated and allowlisted; used as the shell gate. |
| `GET /api/admin/catalog` | `gauntlet.admin-catalog.v1`: sourced content, counts, current game definitions, validation and `gauntlet.content-snapshot.v1` publishing seam. |
| `GET /api/admin/players?offset=0&limit=25` | Bounded identity, campaign/unlock, saved deck-version and match-reference projections. Supabase selects no password columns. |
| `GET /api/admin/matches` | Recent bounded server records, original summaries and provenance with explicit partial-source issues. |
| `GET /api/admin/matches/:matchId` | Existing public record projection, authoritative audit/league evidence, versions and verified archive provenance where available. |
| `GET /api/admin/system` | Sanitized checks, schemas, environment/commit if available and boundaries. |
| Existing `/api/admin/*` operations | Retained behind the same two-ID middleware. No owner-token bypass. |

The catalog snapshot fingerprints only the loaded public content manifest. It is read-only and does not invent a draft record, publish status, release timestamp or rollback capability. Before it becomes an editable source, its coverage must expand to all authored fields (including campaign-only faction definitions and extracted encounter configuration) and bind an explicit engine compatibility contract.

## Incremental path to safe editing

1. **Structured narrative drafts.** Extract an explicit schema for campaign copy, character descriptions, dialogue and asset references; preserve existing IDs. Store drafts separately from the loaded registry. Start with one campaign and require a diff plus validation. Mechanical card/faction fields remain read-only.
2. **Draft → validate → preview/playtest → publish → rollback.** Make validation accept a draft value instead of only module globals. Create immutable content snapshots and a release pointer; preview against isolated account/match storage. Bind engine/content/asset versions, pin rooms to their starting release and record that release in evidence. Rollback switches future rooms to a prior compatible release; it never rewrites matches.
3. **Encounters and game configuration.** Extract currently calculated difficulty/boss/deck plans into validated typed data, preserving formulas and regression fixtures first. Add chapter-level encounter previews and bounds checks before allowing edits. Treat mode enablement as a separate configuration with in-flight room behavior.
4. **Direct typed engine integration.** Establish command, state, authored-effect and published-content schemas across server and browser. Replace card-ID coupling incrementally with reviewed effect definitions and equivalence tests. Do not migrate every mode in one change.
5. **Operational/player repair.** Introduce narrowly scoped previews for a missing consequence receipt, failed archival copy, or a single progression correction. Require a reason and immutable audit receipt; make retry idempotent. Keep the two-account allowlist until there is an explicit need to expand access.

These are the next five smallest high-value capabilities. The intended direction remains:

```text
Admin -> authored content/configuration -> validation -> immutable published version
      -> engine pinned to that version -> authoritative match evidence
```
